# LispGB Constitution

## Core Principles

### I. 正確性第一（テスト ROM による検証）

- エミュレーションの正しさは、公開テスト ROM（Blargg、Mooneye acceptance、
  dmg-acid2 / cgb-acid2）の合否で判定しなければならない（MUST）。「ゲームが動いた」
  という目視確認だけを正しさの根拠にしてはならない。
- 正確性と速度が衝突する場合は、正確性を優先しなければならない（MUST）。正確性を
  落として速度を上げる最適化は、その不合格をユーザーが承認し、記録した場合に限って許可する。
- 既知の不合格テストは、名前と理由を開発文書に一覧で記録しなければならない（MUST）。

**理由**: エミュレーターの価値は実機との一致にあり、客観的な基準がなければ
「RuxBoy と同等」を示せないため。

### II. テスト先行と回帰防止

- コアの各部（CPU、割り込み・タイマー、PPU、APU、MBC、GBC 機能、セーブステート、
  ジョイパッド）は、実装と同時か実装より先に、単体テストまたはテスト ROM による
  自動テストを持たなければならない（MUST）。
- 全テストは1つのコマンド（またはスクリプト）で実行できなければならない（MUST）。
  一度合格したテストが不合格になる変更は、完了扱いにしてはならない。
- テスト ROM はリポジトリに含めず、コミット固定の取得元からスクリプトで取得しなければ
  ならない（MUST）。

**理由**: エミュレーターは部品同士が細かいタイミングで依存し合うので、変更による
退行が起きやすいため。

### III. 実機速度でのリアルタイム動作

- ウィンドウ表示・音声ありの通常実行で、実機と同じ速度（約 59.7fps）を音切れなく
  維持しなければならない（MUST）。ペースは音声出力で保つ。
- 性能上のボトルネックは、推測で直さず、計測（プロファイル・ベンチマーク）してから
  対処しなければならない（MUST）。計測結果は開発文書に残す。
- 処理系の最適化宣言（型宣言、`optimize` 指定など）は、効果が計測で確認できた箇所に
  限って使う（SHOULD）。

**理由**: 「RuxBoy と同等」でありながら、RuxBoy の弱点だった性能を Common Lisp では
解消できるため。

### IV. コアとフロントエンドの分離

- エミュレーションコアは、ウィンドウ、音声デバイス、ファイルシステム、OS API に
  依存してはならない（MUST）。入力はメモリ上のバイト列とボタン状態、出力は
  フレームバッファと音声サンプルとする。
- コアはヘッドレスで動かせなければならない（MUST）。テストとヘッドレスモード
  （`--headless --frames N --screenshot PATH`）は、マルチメディア層なしで動作する。
- セーブステートは、不正な入力を受け取ったときに現在の状態を一切変更せずに拒否
  しなければならない（MUST）。

**理由**: テストのしやすさ、CI でのヘッドレス検証、将来のプラットフォーム追加を
コアに手を入れずに実現するため。

### V. シンプルさと依存の最小化

- 外部ライブラリは、自前で書くと割に合わない領域（マルチメディア層など）に限って
  使う（SHOULD）。依存を追加するときは、理由を計画書に記録しなければならない（MUST）。
- 仕様にない機能（YAGNI）、使い道が1つしかない抽象化、将来のためだけの拡張点を
  追加してはならない（MUST NOT）。
- 複雑さを持ち込む場合は、計画書の Complexity Tracking に理由と、それより単純な
  代案を退けた理由を書かなければならない（MUST）。

**理由**: 依存が少ないほど、ビルドの再現性と複数 OS への展開が容易になるため。

## 技術制約とプラットフォーム

- 実装言語は Common Lisp とする。処理系とライブラリは、Quicklisp 等の標準的な方法で
  取得できるものを使う。
- 対応プラットフォームの優先順位は 1. Linux（Ubuntu、amd64 / arm64）、2. macOS
  （Intel / Apple Silicon）、3. Windows（x64）とする。1つの OS で完成させてから次へ広げる。
- 配布は GitHub Releases で、各プラットフォーム向けの zip に入れたコマンドライン
  アプリとする。
- 設定ファイル等の置き場所は各 OS の慣習に従う（Linux は XDG Base Directory、
  macOS は `~/Library/Application Support/LispGB/`、Windows は `%APPDATA%\LispGB\`）。
- バージョンはセマンティックバージョニング（ビルド番号がある場合は1からの連番）とする。
  ライセンスは MIT とする。
- BIOS（ブート ROM）は使わず、起動直後のレジスタ値を直接設定する。

## 開発ワークフローと厳守事項

- 仕様書、計画書、ドキュメント、ソースコードのコメント、ユーザー向けメッセージは
  日本語で書く。識別子と技術用語は原語のままでよい。
- **コミットは、tasks.md のタスクが1つ完了するごとに行う。** 1タスク＝1コミットとし、
  そのタスクのテストが合格してからコミットする。メッセージの1行目は `T012: Bus とメモリマップを実装`
  のように、タスク ID で始める。
- **プッシュは、その都度ユーザーの明示的な指示があるまで行ってはならない。** 作業継続の許可も、
  コミットの許可も、プッシュの許可ではない（プッシュすると CI が走り、使用量を消費するため）。
- 実際のユーザー名をコード、設定、ドキュメント、コミットに残してはならない。パスは
  `~` / `$HOME` で表す。ただし、git の作者欄（`user.name`）に公開ハンドルの `bubio` を使うことは
  ユーザーが承認している（2026-10-07）。
- README.md には利用者向けの情報だけを書く。開発向けの情報は `docs/dev/` に置く。
- ビルドとテストの手順はローカルと CI で同じにする。複雑な手順はスクリプトにまとめ、
  CI からも同じスクリプトを呼ぶ。
- 市販ゲーム ROM での動作確認が必要になったら、実行前にユーザーに相談する。
- 参照実装は RuxBoy（`~/Develop/ruxboy`）とする。機能や設計で迷ったら RuxBoy の
  挙動と開発文書に合わせる。意図的に変える場合は、その理由を記録する。

## Governance

- 本憲法は、このプロジェクトの他のすべての慣行や文書より優先する。
- 改定は `/speckit-constitution` で行い、変更内容、理由、影響範囲を Sync Impact Report に
  記録する。原則を削除したり意味を変えたりする改定には、ユーザーの承認が必要である。
- バージョン管理: 原則の削除や再定義は MAJOR、原則や節の追加・大幅な拡張は MINOR、
  文言の明確化や誤字の修正は PATCH とする。
- `/speckit-plan` の Constitution Check と `/speckit-analyze` では、各原則への適合を確認
  しなければならない。違反がある場合は、Complexity Tracking に理由を書くか、設計を
  見直す。
